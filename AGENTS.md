# AGENTS.md

## Project

This is Verse Listener: a dependency-light, browser-only PWA for listening to Russian or English sermons, detecting spoken Bible references, and privately reporting missed detections with recent microphone audio.

This guide combines the reusable working, safety, testing, browser-control, screenshot, and communication protocols from Automation Core and Sermon App. Keep only Verse Listener-specific behavior here; project-specific Electron, React Native, Expo, native iOS, Office, and sibling-project release rules remain in the projects that own them.

## Project context and source of truth

- Treat the current repository files as source truth. Inspect the owning HTML, CSS, JavaScript module, test, and service-worker code before editing behavior.
- The application is static HTML/CSS/JavaScript with no runtime package dependencies.
- `src/bibleVerseParser.ts` and its imports own parser source. `parser.js` is generated by `npm run compile:parser`; do not hand-edit it.
- `index.html`, `styles.css`, and the browser modules imported by `app.js` own the production UI and runtime.
- `audio-ring-buffer.js` and `audio-worklet.js` own rolling feedback capture. Keep unrelated audio-test behavior in a focused sibling module.
- `feedback-store.js`, `feedback-api.js`, `feedback-ui.js`, and `supabase/` own private feedback queueing and delivery.
- `service-worker.js`, `manifest.webmanifest`, and versioned asset URLs own install/offline behavior. Keep their cache versions aligned after shipping a changed asset.
- `source-context.js` owns the downloadable current-source inventory. Add material source or test files to that inventory.

## Working style

- Keep responses short, direct, and practical.
- For non-trivial work, create a simple 3-7 step plan before editing and keep it current.
- Break large workflows into small, independently useful slices with one clear verification gate each.
- Before changing existing files, inspect the current files, current diff, and relevant history first.
- Prefer small focused patches over large rewrites.
- Design new modules under 200 lines when clean helper or controller boundaries make that practical.
- Do not trim or contort good code merely to meet a line target. Treat 500+ lines as requiring a split unless the file is generated, a plain data table, or the exception is explained in the change summary.
- Keep browser concerns modular: markup, presentation, audio/session control, persistence, and parser logic should not collapse into one file.
- Avoid unused variables, broken imports, unsafe implicit globals, and duplicated state ownership.
- Do not add unrelated features while fixing a bug.
- Preserve existing project patterns unless there is a clear reason to change them.
- Give every interactive control a pointer cursor and clear hover, active, focus-visible, and disabled states unless the surface handles them globally.

## Regression containment

- For bug fixes, change only the smallest code path proven to cause the bug. Do not refactor adjacent parsing, audio, feedback, PWA, styling, or lifecycle behavior unless the requested fix requires it.
- Treat unrelated working behavior and existing user changes as protected scope.
- If the user says an earlier version worked, compare with that known-good implementation first. Prefer restoring proven behavior and applying only the requested delta.
- If an attempted fix fails or creates a regression, stop stacking guesses. Remove the unnecessary changes from that attempt and re-investigate from direct evidence.
- Trace shared state through every affected start, stop, pause, resume, record, playback, persistence, visibility, and cleanup path before patching lifecycle bugs.
- Keep performance fixes behavior-preserving. Do not change approved layout, colors, proportions, or interaction timing merely because those surfaces are nearby.
- Before finishing, review the complete diff and remove every changed line that is not necessary for the stated request.

## Implementation protocol

- Implement features end-to-end, not half-baked.
- Complete the loading, permission, empty, active, stopped, error, retry, playback, visibility, and cleanup states needed for the requested workflow.
- Build non-trivial work modularly from the first draft instead of parking several controllers and UI concerns in `app.js`.
- Before adding to a large file, decide whether a focused sibling module keeps ownership clearer.
- Before finishing a feature, check the full applicable lifecycle: create/start, read/display, update, stop/delete, reload, offline behavior, and old-data cleanup.
- Keep UI actions visually instant. Update local controls immediately, then perform asynchronous browser or network work with useful error and rollback feedback.
- Preserve separate ownership for verse detection, test audio, rolling feedback audio, and submitted feedback unless an explicit product decision joins them.
- If a feature is cloud-backed, include the required data layer and offline/retry behavior rather than leaving a misleading local-only path.
- When editing a shared entity or format, update every dependent reader, cache entry, test, and source-context reference.

## UI design workflow

- Treat visual design, spacing, colors, layout, responsive behavior, light/dark polish, and control-state requests as design work.
- Existing production UI is the source of truth for existing surfaces. Inspect the owning markup and CSS before changing it.
- Preserve the compact centered mobile shell, safe-area padding, responsive desktop frame, restrained card hierarchy, and both light and dark themes unless the user requests a redesign.
- Do not add explanatory banners, extra cards, decorative copy, or duplicate variants unless the workflow requires them or the user asks for them.
- Reuse current control weights, section borders, row heights, radii, spacing, and color variables before inventing new visual language.
- Keep important controls reliably tappable on the first touch and operable by keyboard.
- Use semantic HTML, explicit labels, `aria-live` only for meaningful status, `aria-pressed` for toggles, and accurate disabled/hidden states.
- Purposeful lightweight entry, exit, pressed, and state-change motion is expected for custom feedback or expanding UI, while respecting `prefers-reduced-motion`.
- Test narrow mobile widths, the 468px shell, light and dark themes, long status text, permission denial, and representative active states when geometry can change.
- For a material production UI change, verify the real rendered page at interaction depth; a static source check alone is not acceptance.

## Browser audio and speech rules

- Be especially careful with microphone permission, speech recognition, live monitoring, recording, playback, raw audio, browser visibility, and mobile/PWA lifecycle behavior.
- Microphone features must require an explicit user action and a secure context. Never request microphone permission on page load.
- Feature-detect `navigator.mediaDevices`, `getUserMedia`, `SpeechRecognition`, `AudioContext`, and `MediaRecorder` as applicable, and show a specific useful unsupported or permission message.
- Keep live monitoring opt-in and warn about headphones or acoustic feedback. Never silently route a live microphone to speakers.
- Preserve the existing speech-oriented constraints for verse listening unless the requested behavior needs a separate input profile.
- Do not let the verse listener and a test recorder compete for microphone ownership. Stop and release the previous owner before starting the other workflow.
- Treat autoplay policies as part of the design. Start audible monitoring and recording playback from direct user gestures and handle rejected `play()` promises.
- On stop, page hide, replacement, or failure, release every owned media track, `AudioContext`, analyser/source connection, animation frame, timer, event listener, and object URL.
- If a track ends outside the UI, transition controls and status to a truthful stopped state.
- Do not log, upload, persist, or include raw audio or transcript contents anywhere except the existing explicitly authorized feedback workflow.
- Keep test recordings local to the current page unless the user explicitly asks for durable storage or sharing.

## Audio performance guardrails

- Treat level meters and playback progress as high-frequency UI data. Keep them inside the smallest owning module and DOM subtree.
- Use one animation-frame loop for visible meter updates; do not propagate per-frame values through unrelated application state.
- Pause visual meter work while the document is hidden, but do not silently terminate an active recording solely because the screen dims or the user briefly backgrounds the PWA.
- Re-synchronize the meter once when the page becomes visible again.
- Do not add high-frequency console logs for audio samples, waveform frames, meter values, or polling.
- Reuse typed arrays for analyser reads and avoid per-frame DOM creation.
- Prefer compressed `MediaRecorder` output when available. Do not retain unbounded PCM data in memory.
- Revoke the previous recording URL when replacing or discarding it.
- Red flags include multiple active microphone streams, multiple animation loops, hidden meters still rendering, unreleased object URLs, broad per-frame rerenders, or playback nodes connected after stop.

## Data and service safety

- Be careful with auth, IndexedDB, storage, sync, file operations, credentials, browser-native behavior, and release tooling.
- Do not edit `.env`, credential files, secrets, or files under `data/` that look like credentials.
- Do not change dependencies without checking `package.json` first. Prefer the package manager already used by the repository.
- Do not run deploy, publish, release, destructive database, or destructive storage commands unless specifically asked.
- Never revert user changes unless explicitly requested.
- Preserve the local-first feedback contract: a failed delivery stays queued privately and retries later.
- For Supabase changes, inspect the current schema/function ownership, make the smallest task-scoped change, and verify the live shape when the user authorizes deployment.
- Never expose private feedback audio, signed URLs, tokens, authorization headers, or credentials in logs, fixtures, source bundles, or responses.

## PWA and cache workflow

- Treat the service worker as part of every changed browser module's delivery path.
- When a cached production asset changes, bump the shared cache/query version consistently in `index.html`, JavaScript imports, worklet URLs, `service-worker.js`, and `manifest.webmanifest` where applicable.
- Add new offline-required modules to the application shell and static contract test.
- Keep network-first behavior and offline fallback intentional; do not let stale cache entries mask current code during verification.
- Do not claim an installed PWA is updated until the new worker and versioned assets can be fetched.
- Publishing is a separate authorized action. Local implementation and verification do not imply deployment.

- Do not generate broad feedback snapshots by default.

## Screenshot efficiency protocol

- Default to zero screenshots. Prefer source inspection, semantic DOM state, browser APIs, JSON, logs, and deterministic commands.
- Use screenshots only when the answer materially depends on appearance, such as layout, spacing, clipping, color, animation, an unexpected visual state, or final acceptance of a visual fix.
- Before each screenshot, identify the exact visual question it will answer. Reuse the newest relevant capture instead of taking another.
- Never use screenshots for polling, routine status, or facts and controls already exposed through structured state.
- For a visual bug, normally use one baseline screenshot and one post-fix proof. Take another only when that proof reveals a concrete remaining defect.
- Prefer the smallest relevant crop, detail level, and resolution supported. Avoid high-detail desktop captures unless required.
- Soft target: zero screenshots for non-visual work and 2-5 screenshots for ordinary visual debugging.
- Hard limit: at most 40 screenshot captures or explicit model image inspections combined per user-requested run. Compaction, retries, reloads, and substeps do not reset the count.
- The 40-image limit is an emergency ceiling, never a quota. At the limit, continue with structured evidence or report the remaining visual blocker.

## Research-first and testability workflow

- When a feature depends on a browser API or external runtime, inspect the real supported contract before implementing it.
- Prove the smallest observable boundary first: capability and permission, then input/start, then state and completion, then playback/delivery, then cleanup.
- Implement from observed browser behavior rather than guessed event order, MIME support, timing, or permission semantics.
- Make every slice independently observable through semantic state, concise status text, stable element IDs, and deterministic tests.
- Use structured DOM/browser diagnostics for repeated checks. Use visual control only when appearance or trusted user input materially affects the result.
- If browser control stalls twice, stop reconnecting and use the proven programmatic boundary or report the blocker.
- Keep one dedicated local page for an unresolved issue; do not multiply tabs or permission prompts.
- Final end-to-end testing confirms already-proven pieces. It should not be the first place individual audio mechanisms are diagnosed.

## Automation Core, browser, and Windows control

- Prefer code, project scripts, logs, browser APIs, and direct diagnostics over browser or Windows UI control.
- If shared Automation Core capabilities are needed, work from `C:\Users\pshic_\OneDrive\Documents\Automation Core`, run `npm run core:tools -- list`, and use only the documented command matching the authorized task.
- Before creating temporary browser, process, clipboard, window, or log diagnostics through Automation Core, run `npm run core:tools -- umf.captureState --compact` and inspect the current state.
- For browser work, prefer direct semantic DOM, console, protocol, and media-state inspection. Reacquire the page after navigation or reload.
- Activate browser control only for the exact browser interaction being performed. Release or close its claimed tab immediately afterward, and never leave a tab claimed while researching outside the browser, coding, editing files, running checks, reading logs, or waiting.
- Reacquire the same tab only when a later visual or interactive verification step genuinely needs browser control; do not keep a claim active merely to preserve context.
- Use Chrome Control only for initial orientation, a permission/trusted-input interaction, or a visual fact that code cannot establish. Claim one tab only for that interaction and release it immediately.
- Use Computer Use only for a brief prepared Windows interaction or final visual acceptance that code and browser controls cannot perform. Release it immediately afterward.
- Treat Computer Use as a one-action lease: name the exact visual fact or input first, finish or pause all code, shell, browser, memory, and planning work, then observe, perform at most one prepared interaction, verify it, and release/reset in the same sequence.
- After a Computer Use observation or interaction, release/reset it before any other tool call, progress update, wait, memory lookup, or final response. Never preserve window handles, coordinates, or element indexes for later unrelated work.
- If the user may be actively using the computer, skip Computer Use unless they explicitly request live interaction.
- Keep temporary tabs, dialogs, servers, processes, and windows to the minimum needed and close only the artifacts created for this task.

## Testing workflow

- Do not run build, deploy, or publish commands unless the user explicitly asks. Compilation and checks are allowed.
- Establish the current test baseline before non-trivial behavior changes when practical.
- After normal code edits, run `npm test`.
- After parser source edits, run `npm run compile:parser` before `npm test`.
- Test every implemented behavior before handoff. Prefer deterministic module and semantic DOM checks; add rendered-page inspection when layout or interaction is part of the claim.
- For audio UI, verify capability absence, permission denial, start, level updates, monitor on/off, recording start/stop, playback readiness, replacement, mutual exclusion, track-ended cleanup, page hide/show, and page teardown as applicable.
- Trigger every safe new control once in a real browser or a faithful browser harness; source matching alone is not acceptance.
- Keep static checks focused and non-repetitive. Do not rerun unchanged checks hoping for a different result.
- For one specific unresolved live bug, make no more than five consecutive attempts. Every retry after the first must follow an evidence-backed change.
- Mention failed checks only if they could not be fixed.
- Always close temporary test servers, tabs, streams, dialogs, and processes before handoff.

## Runtime logging workflow

- Use concise development logs only at meaningful lifecycle boundaries and state transitions.
- Use one stable feature prefix, short event names, and small structured fields containing state, timing, capability, and sanitized errors.
- Never log tokens, authorization headers, passwords, secrets, signed URLs, raw audio, transcripts, feedback notes, or credential files.
- Do not log animation frames, meter values, audio samples, waveform data, or high-frequency polling.
- Remove temporary verbose diagnostics after verification or leave them disabled behind an explicit debug switch.

## Planning workflow

- Keep at most one step in progress and update the plan at meaningful milestones instead of narrating every command.
- If a project-owned Notion page or issue tracker is later designated, scan its Ready for Codex area first and keep the active plan synchronized there. Do not invent or reuse a sibling project's page.

## Codex live-update style

When working, use short emoji bullets rather than long progress paragraphs.

Preferred format:

- 🔎 Inspecting: short plain-English description.
- 🧠 Found: short issue summary.
- 🛠️ Changing: short patch summary.
- 🧪 Checking: command or verification.
- ✅ Done: final result.

Rules:

- Keep each update to 1-3 bullets and each bullet under 16 words when practical.
- Use one bullet when one is enough.
- Do not include long file paths or narrate every command.
- Do not repeat the same idea across updates.

## Codex final summary style

- Use a `Summary` heading followed by 1-5 short emoji lines.
- Make every line outcome-focused, distinct, and easy to scan.
- Omit a Try section unless the user explicitly asks for testing steps.
- Omit file paths, line numbers, changed-file lists, and internal implementation details unless requested.
- Do not mention passing checks, tests, commits, releases, or deployment unless requested.
- Mention failed checks only when they remain relevant.
